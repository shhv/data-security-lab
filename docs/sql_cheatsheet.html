For learning fast and for live debugging on customer calls. Read-only first, always.

2 · How SQL actually runs (order)

FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
  • That's why a SELECT alias can't be used in WHERE: WHERE runs first. Repeat the expression or wrap it in a CTE.
  • Window functions run at the SELECT step. To filter on them, wrap in a CTE, then use WHERE rn = 1.

3 · Live-debug playbook (customer call)

  1. Orient. List tables, describe the 1–2 that matter (dialect table below). Ask: "what's one row in this table?"
  2. Sample. SELECT * … LIMIT 5. Look at real values, NULLs, date formats and time zones.
  3. Count. SELECT COUNT(*), then add filters one at a time. The filter where the count changes unexpectedly is your bug.
  4. Isolate. Pick one specific user or id the customer mentions and follow it through every table.
  5. Check joins. Count rows before and after each join. If the count grows, the join is duplicating rows (one-to-many).
  6. Check NULLs and types. WHERE col IS NULL; text vs number; '2026-1-5' vs '2026-01-05'.
  7. State the answer as a query. Read it back: "this shows X users who did Y since Z." Save it.

Safety on a live system

  • Use a read-only account or replica when possible. Start every query with SELECT.
  • Always add LIMIT (or TOP) while exploring big tables.
  • Before any UPDATE/DELETE: run the same WHERE as a SELECT COUNT(*) first, and wrap it in BEGIN; … ROLLBACK; until it's verified.
  • Never run UPDATE/DELETE without WHERE.
  • Screen-sharing? Select only the columns you need, and don't show raw PII (SSNs, emails). Count or mask instead.
  • Slow query? EXPLAIN it before rerunning. Check for a missing index on the WHERE or JOIN column.

4 · Gotchas that cause wrong answers

SymptomCause / fix
WHERE x = NULL returns nothingUse IS NULL. NULL never equals anything, not even NULL.
NOT IN (subquery) returns nothingSubquery contains a NULL. Use NOT EXISTS.
LEFT JOIN acts like an inner joinA WHERE condition on the right table drops NULL rows. Move it into ON.
Totals too big after a joinJoin fan-out. Aggregate in a CTE first, then join.
COUNT(col) < COUNT(*)COUNT(col) skips NULLs. Choose on purpose.
Ratio shows 0Integer division. Use 1.0 * a / b.
Dates sort or compare oddlyText dates must be YYYY-MM-DD. Watch time zones (UTC vs local).
Missing groups with zero rowsInner join drops them. LEFT JOIN from the full list, then COALESCE(COUNT…,0).
DISTINCT "fixes" duplicatesIt hides a bad join. Find out why rows duplicated.
Off by one dayts < '2026-11-14' excludes that whole day. Prefer < next day.

6 · Templates you'll reuse (identity / security)

-- Latest sign-in per user
WITH r AS (SELECT *, ROW_NUMBER() OVER
  (PARTITION BY user_id ORDER BY ts DESC) rn FROM sign_ins)
SELECT * FROM r WHERE rn = 1;

-- Users with no sign-in at all (orphan / dormant)
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM sign_ins s WHERE s.user_id = u.id);

-- Failures per IP in the last day; spray = many users
SELECT ip, COUNT(*) fails, COUNT(DISTINCT user_id) users
FROM sign_ins WHERE result='failure' AND ts >= :since
GROUP BY ip HAVING COUNT(DISTINCT user_id) >= 10;

-- Time since the previous event for the same user
SELECT user_id, ts, country,
  LAG(ts) OVER (PARTITION BY user_id ORDER BY ts) prev_ts
FROM sign_ins;

-- Expand nested groups
WITH RECURSIVE m(id) AS (
  SELECT member_id FROM group_members WHERE group_id = :g
  UNION
  SELECT gm.member_id FROM m JOIN group_members gm ON gm.group_id = m.id)
SELECT * FROM m;

-- Duplicate assignments
SELECT app_id, principal_id, COUNT(*) FROM app_assignments
GROUP BY app_id, principal_id HAVING COUNT(*) > 1;

7 · Questions to ask the customer first

  • Which database and version? Read-only access or production?
  • What's the grain: one row per what (per user? per event? per day)?
  • Which time zone are timestamps stored in?
  • What number do they expect, and what do they see? Get one concrete example id.
  • Has anything changed recently (deploy, migration, sync job)?
